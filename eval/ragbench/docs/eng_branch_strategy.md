# 브랜치 전략 및 커밋 규칙

작성: SRE팀 · 적용 대상: 데이터허브(DataHub) 백엔드·프론트엔드 저장소 · 최종 수정 2025-11-20

## 1. 개요
데이터허브 저장소는 트렁크 기반 개발(Trunk-Based Development)을 따릅니다. `main`이 항상 배포 가능한 상태를 유지하고, 기능 개발은 짧게 유지되는 브랜치에서 진행합니다.

## 2. 브랜치 종류

| 브랜치 | 이름 규칙 | 분기 기준 | 머지 대상 |
|---|---|---|---|
| main | `main` | - | - |
| 기능 | `feature/<Jira키>-<요약>` | main | main |
| 버그 수정 | `fix/<Jira키>-<요약>` | main | main |
| 릴리스 | `release/YYYY.MM.DD` | main | (머지하지 않음) |
| 핫픽스 | `hotfix/<Jira키>-<요약>` | release | release, main |

- 예: `feature/DH-1532-dashboard-filter`, `release/2026.10.08`
- 브랜치 이름에는 영문 소문자, 숫자, 하이픈(-)만 사용합니다.

## 3. 기능 브랜치 운영
- 기능 브랜치는 3일 이내에 머지하는 것을 목표로 합니다.
- 브랜치를 1주일 이상 유지해야 하는 경우 최소 이틀에 한 번 `main`을 rebase하여 충돌을 줄입니다.
- 완성되지 않은 기능은 기능 플래그(Feature Flag) 뒤에 숨긴 상태로 머지할 수 있습니다. 기능 플래그는 LaunchDarkly에서 관리합니다.

## 4. 머지 방식
- `main`으로의 머지는 Squash and merge만 허용합니다. 따라서 PR 제목이 곧 커밋 메시지가 됩니다.
- Rebase and merge, Merge commit 방식은 저장소 설정에서 비활성화되어 있습니다.
- 머지 후 원격 기능 브랜치는 자동으로 삭제됩니다.

## 5. 릴리스 브랜치
1. 릴리스 브랜치는 정기 배포일(화·목) 오전 10시에 SRE팀의 릴리스 봇이 `main`에서 자동으로 생성합니다.
2. 릴리스 브랜치가 생성된 뒤에는 기능 변경을 추가하지 않습니다.
3. 릴리스 브랜치에서 발견된 버그는 `hotfix/` 브랜치로 수정한 뒤 릴리스 브랜치에 머지하고, 같은 수정을 `main`에도 cherry-pick 합니다.
4. 배포가 끝나면 릴리스 커밋에 `v<major>.<minor>.<patch>` 형식의 태그를 붙입니다. 예: `v4.12.0`

## 6. 커밋 메시지 규칙
커밋 메시지는 Conventional Commits 형식을 따릅니다.

```
<type>(<scope>): <설명> [Jira키]
```

| type | 용도 |
|---|---|
| feat | 새로운 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| docs | 문서 수정 |
| test | 테스트 추가·수정 |
| chore | 빌드, 설정, 의존성 변경 |

예: `fix(api): 대시보드 조회 시 타임존 오류 수정 [DH-1588]`

## 7. 금지 사항
- `main`과 `release/*` 브랜치에 force push 하는 것은 금지되어 있으며, 저장소 보호 규칙으로 차단됩니다.
- 비밀번호, API 키, 인증서 등 비밀 정보는 커밋하지 않습니다. 커밋 시 gitleaks 검사가 자동으로 실행되며, 비밀 정보가 발견되면 push가 거부됩니다.
- 실수로 비밀 정보를 커밋했다면 즉시 해당 키를 폐기(rotate)하고 정보보호팀에 알립니다.
