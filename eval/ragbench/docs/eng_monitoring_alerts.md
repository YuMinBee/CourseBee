# 모니터링 및 알람 기준

SRE팀 관리 문서 | 버전 3.1 | 개정일 2026년 1월 15일

## 1. 모니터링 구성
- 지표 수집: Prometheus (수집 주기 30초, 보관 기간 15일). 장기 보관 지표는 Thanos에 13개월 보관한다.
- 시각화: Grafana (https://grafana.hanbit.internal). 서비스별 기본 대시보드는 SRE팀이 제공한다.
- 로그: Loki. 운영 로그 보관 기간은 30일이다.
- 알람 전달: Alertmanager → PagerDuty(호출) / Slack(알림).

## 2. 알람 등급

| 등급 | 전달 방식 | 대응 |
|---|---|---|
| Warning | Slack #alerts-warn 채널 메시지 | 업무 시간 내 확인, 필요 시 Jira 티켓 생성 |
| Critical | PagerDuty로 on-call 호출 + Slack #alerts-crit | 즉시 대응, 「서비스 장애 대응 Runbook」 적용 |

## 3. 표준 알람 기준
아래 기준은 모든 운영 서비스에 기본으로 적용된다. 서비스 특성상 다른 기준이 필요하면 7장의 절차로 변경을 요청한다.

| 지표 | Warning | Critical |
|---|---|---|
| CPU 사용률 | 80% 이상 10분 지속 | 95% 이상 5분 지속 |
| 메모리 사용률 | 85% 이상 10분 지속 | 95% 이상 5분 지속 |
| 디스크 사용률 | 80% 이상 | 90% 이상 |
| API 5xx 에러율 | 1% 이상 5분 지속 | 5% 이상 3분 지속 |
| API p95 응답시간 | 800ms 이상 10분 지속 | 2,000ms 이상 5분 지속 |
| Kafka consumer lag | 10,000건 이상 | 100,000건 이상 |
| TLS 인증서 만료 | 만료 30일 전 | 만료 7일 전 |
| 헬스체크 실패 | - | 3회 연속 실패 |

※ 배포 중 자동 롤백 기준(5xx 에러율 2% 등)은 알람 기준과 별개로 「운영 배포 및 롤백 가이드」에서 정한다.

## 4. 알람 메시지 필수 항목
모든 알람 규칙에는 다음 항목을 반드시 포함한다.
- `summary`: 한 줄 요약
- `severity`: warning 또는 critical
- `team`: 담당 팀
- `runbook_url`: 대응 방법이 적힌 Confluence 문서 링크

`runbook_url`이 없는 알람 규칙은 CI 검사에서 거부된다.

## 5. 알람 억제(silence)
- 정기 배포 중에는 배포 대상 서비스의 Warning 알람이 15분 동안 자동으로 억제된다. Critical 알람은 억제하지 않는다.
- 계획된 점검이 있으면 시작 1시간 전까지 Alertmanager에 silence를 등록하고, #sre 채널에 점검 시간과 대상을 공지한다.
- 2시간을 넘는 silence는 SRE팀 승인이 필요하다.

## 6. 알람 품질 관리
- 오탐 비율이 높은 알람은 매월 on-call 회고에서 검토한다.
- 3개월 동안 한 번도 발생하지 않은 알람은 분기마다 필요성을 재검토한다.

## 7. 알람 추가·변경 절차
1. `alert-rules` 저장소에 알람 규칙 변경 PR을 올린다.
2. PR 설명에 변경 이유와 최근 2주 지표 그래프를 첨부한다.
3. SRE팀 1명 이상이 승인하면 머지한다.
4. 머지 후 10분 이내에 Alertmanager에 자동 반영된다.
5. 전사 표준 기준(3장)을 바꾸는 경우에는 엔지니어링 주간 회의에서 공지한 뒤 반영한다.
