# 코드 리뷰 가이드라인

> 기술본부 공통 가이드 · Confluence ENG 스페이스 · 최종 수정 2026-02-10 · 작성: 플랫폼팀 이서연

## 왜 코드 리뷰를 하나요?
코드 리뷰는 버그를 잡는 것뿐 아니라 지식을 공유하고 코드베이스의 일관성을 지키기 위한 활동입니다. 리뷰어는 "내가 이 코드를 새벽 3시에 장애 대응하면서 읽어야 한다면?"이라는 관점으로 봐 주세요.

## 기본 규칙
1. `main` 브랜치에 직접 push하는 것은 금지되어 있습니다. 모든 변경은 Pull Request(PR)로 올립니다.
2. PR은 최소 1명의 승인(Approve)이 있어야 머지할 수 있습니다.
3. 아래 영역을 변경하는 PR은 2명 이상의 승인이 필요하며, 그중 1명은 CODEOWNERS에 등록된 담당자여야 합니다.
   - 결제·과금 모듈 (`billing/`)
   - 인증·권한 모듈 (`auth/`)
   - DB 스키마 마이그레이션 (`migrations/`)
4. 본인이 올린 PR을 본인이 승인할 수 없습니다.
5. CI(빌드, 단위 테스트, lint)가 모두 통과해야 머지 버튼이 활성화됩니다. 신규 코드의 테스트 커버리지는 70% 이상이어야 합니다.

## PR 작성 요령
- PR 하나의 변경량은 400줄 이하를 권장합니다. 그보다 크면 기능 단위로 나눠 주세요. (자동 생성 코드, lock 파일은 제외)
- PR 제목에는 Jira 이슈 키를 넣습니다. 예: `[DH-1532] 대시보드 필터 저장 기능 추가`
- 본문 템플릿의 '변경 이유', '테스트 방법', '배포 시 주의사항'을 반드시 채웁니다.
- UI 변경은 변경 전·후 스크린샷을 첨부합니다.

## 리뷰어 지정과 응답 시간
- 리뷰어는 리뷰 배정 봇 `review-roulette`이 팀 내에서 자동으로 2명을 지정합니다. 필요하면 작성자가 추가로 지정할 수 있습니다.
- 리뷰 요청을 받은 사람은 1영업일 이내에 첫 리뷰 코멘트를 남겨야 합니다.
- 1영업일 안에 리뷰가 어렵다면 PR에 그 사실을 코멘트로 알리고, `review-roulette`에 재배정을 요청합니다.

## 코멘트 작성 규칙
코멘트 앞에는 다음 접두어를 붙여 의도를 분명히 합니다.

| 접두어 | 의미 | 머지 전 반영 |
|---|---|---|
| [must] | 버그, 보안 문제 등 반드시 고쳐야 하는 사항 | 필수 |
| [should] | 강하게 권장하지만 논의 가능한 사항 | 권장 |
| [nit] | 사소한 스타일, 오타 | 선택 |
| [question] | 이해를 위한 질문 | 답변 필요 |

- 사람이 아닌 코드에 대해 이야기합니다. "왜 이렇게 했어요?" 대신 "이 부분은 ○○ 때문에 △△가 더 안전할 것 같아요"처럼 씁니다.
- 스타일 관련 지적은 가능하면 lint 규칙으로 자동화합니다.

## 긴급 핫픽스
P1·P2 장애 대응을 위한 핫픽스는 승인 1명만으로 머지할 수 있습니다. 이 경우 머지 후 2영업일 이내에 사후 리뷰를 받아야 하며, 사후 리뷰에서 나온 [must] 코멘트는 별도 PR로 반영합니다.

## 머지 방식
머지 방식과 브랜치 규칙은 「브랜치 전략 및 커밋 규칙」 문서를 참고하세요.
