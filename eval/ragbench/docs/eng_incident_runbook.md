# 서비스 장애 대응 Runbook

| 항목 | 내용 |
|---|---|
| 문서 ID | ENG-RB-001 |
| 소관 | SRE팀 |
| 적용 서비스 | 데이터허브(DataHub) 운영 환경 전체 |
| 최종 개정 | 2026-03-16 |

## 1. 장애 등급 정의

| 등급 | 정의 | 예시 |
|---|---|---|
| P1 | 서비스 전체 중단, 데이터 유실, 보안 침해로 인한 서비스 중단 | 전 고객 로그인 불가, 데이터 손상 |
| P2 | 핵심 기능 장애 또는 일부 고객 서비스 불가 | 대시보드 조회 실패, 특정 리전 장애 |
| P3 | 일부 기능 성능 저하, 우회 방법 존재 | 리포트 내보내기 지연 |
| P4 | 고객 영향이 거의 없는 경미한 문제 | 관리자 화면 오타, 로그 누락 |

등급이 애매하면 높은 등급으로 먼저 선언하고, 상황을 파악한 뒤 낮춘다.

## 2. 대응 목표 (SLA)

| 등급 | 최초 응답 | 복구 목표 | 상황 공유 주기 |
|---|---|---|---|
| P1 | 15분 이내 | 4시간 이내 | 30분마다 |
| P2 | 30분 이내 | 8시간 이내 | 1시간마다 |
| P3 | 4시간 이내 | 3영업일 이내 | 일 1회 |
| P4 | 1영업일 이내 | 다음 정기 릴리스 | - |

※ 최초 응답은 on-call 담당자가 알람을 확인(ack)하고 대응을 시작한 시점을 말한다.

## 3. 대응 절차
1. **탐지**: 모니터링 알람, 고객 문의(CS팀), 내부 제보로 장애를 인지한다.
2. **확인(ack)**: 1차 on-call이 PagerDuty 호출을 확인하고 영향 범위를 파악한다.
3. **등급 선언**: 1차 on-call이 등급을 판단하여 Slack #incident 채널에 선언한다.
4. **지휘 체계 구성 (P1·P2)**: Incident Commander(IC)를 지정한다. 기본 IC는 SRE팀 2차 on-call이다. IC는 `#inc-YYYYMMDD-<요약>` 형식의 전용 Slack 채널과 Zoom 워룸을 연다.
5. **상황 공유**: IC는 등급별 공유 주기에 맞춰 전용 채널에 현재 상황, 조치 내용, 다음 공유 시각을 올린다.
6. **고객 공지**: P1·P2는 CS팀이 장애 선언 후 30분 이내에 상태 페이지(status.hanbitdata.co.kr)에 공지한다.
7. **복구**: 최근 배포가 원인으로 의심되면 원인 분석보다 롤백을 먼저 한다. 롤백 방법은 「운영 배포 및 롤백 가이드」를 따른다.
8. **종료 선언**: 지표가 30분 이상 정상을 유지하면 IC가 장애 종료를 선언한다.
9. **포스트모템**: P1·P2 장애는 종료 후 5영업일 이내에 포스트모템 문서를 작성하고 리뷰 회의를 연다.

## 3-1. P1·P2 장애 시 역할

| 역할 | 담당 | 하는 일 |
|---|---|---|
| Incident Commander(IC) | SRE팀 2차 on-call (기본) | 전체 지휘, 의사결정, 상황 공유, 종료 선언 |
| 기술 대응 리드 | 장애 서비스 담당 팀의 1차 on-call | 원인 파악, 롤백·복구 작업 실행 |
| 커뮤니케이션 담당 | CS팀 당직자 | 상태 페이지 공지, 주요 고객 개별 연락 |
| 기록 담당(Scribe) | IC가 지정 | 타임라인 기록, 결정 사항과 근거 기록 |

- IC는 직접 복구 작업을 하지 않는 것을 원칙으로 한다. IC가 작업에 몰두하면 전체 상황을 놓치기 쉽기 때문이다.
- 장애가 4시간 이상 길어지면 IC와 기술 대응 리드는 교대 인력을 지정하여 휴식을 취한다.
- 워룸에는 장애 대응에 필요한 사람만 참여하고, 상황이 궁금한 사람은 전용 채널을 읽기만 한다.

## 4. 에스컬레이션
- 1차 on-call이 호출 후 15분 안에 확인하지 않으면 PagerDuty가 2차 on-call을 자동 호출한다.
- 2차 on-call도 15분 안에 확인하지 않으면 해당 팀장에게 전화가 간다.
- P1 장애가 1시간 이상 지속되면 IC는 CTO에게 직접 보고한다.

## 5. 포스트모템 원칙
- 비난하지 않는(blameless) 원칙으로 작성한다. 개인의 실수가 아니라 실수를 가능하게 한 시스템을 분석한다.
- 필수 항목: 타임라인, 고객 영향(시간·범위), 근본 원인, 잘한 점, 개선할 점, 액션 아이템(담당자·기한).
- 액션 아이템은 Jira에 등록하고, 완료될 때까지 매주 엔지니어링 주간 회의에서 추적한다.

## 6. 유형별 1차 조치 체크리스트

### 6.1 배포 직후 에러 증가
- [ ] 최근 2시간 이내 배포 여부를 #deploy 채널에서 확인한다.
- [ ] 배포가 있었다면 원인 분석보다 롤백을 먼저 진행한다.
- [ ] 롤백 후 에러율이 정상으로 돌아오지 않으면 다른 원인을 찾는다.

### 6.2 DB 지연 또는 커넥션 오류
- [ ] Grafana 'DB Overview'에서 커넥션 풀 사용률, 슬로우 쿼리, 복제 지연을 확인한다.
- [ ] 장시간 실행 중인 쿼리가 있으면 DBA와 협의하여 종료한다. 임의로 종료하지 않는다.
- [ ] 배치 작업이 원인이면 배치를 일시 중지한다.

### 6.3 외부 서비스 장애
- [ ] 클라우드 사업자와 외부 API 제공사의 상태 페이지를 확인한다.
- [ ] 외부 장애로 확인되면 서킷 브레이커가 동작했는지 보고, 고객 공지 문구에 외부 원인임을 밝힌다.

### 6.4 보안 침해 의심
- [ ] 서비스 장애와 함께 침해가 의심되면 즉시 정보보호팀 핫라인으로 연락한다.
- [ ] 증거 보존을 위해 의심 서버를 재시작하거나 삭제하지 않는다.

## 7. 상황 공유 템플릿
IC는 전용 채널에 아래 형식으로 상황을 공유한다.

```
[P1] 2026-03-16 14:20 상황 공유 (3차)
- 현재 상태: 복구 진행 중 / 고객 영향: 대시보드 조회 실패 (약 30%)
- 지금까지 한 조치: 14:05 v4.3.1 롤백 완료
- 다음 조치: DB 커넥션 수 모니터링, 원인 분석
- 다음 공유: 14:50
```
